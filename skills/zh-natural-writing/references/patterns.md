# 常见问题和替代表达

这个文件只在需要审校、批量改写或解释修改理由时读取。普通短文本改写不必加载。

## 先删再改

很多 AI 味不是词不好，而是句子本来就没信息量。遇到这类句子，优先删除，不要改写。

| 原句 | 处理 |
| --- | --- |
| 这不仅提升了用户体验，也为后续发展奠定了坚实基础。 | 如果没有具体事实，删。 |
| 该方案具有重要意义和广泛应用前景。 | 说清楚意义在哪里；说不清就删。 |
| 我们将持续优化，不断提升产品能力。 | 改成具体下一步；没有下一步就删。 |
| 这体现了团队对用户需求的深刻理解。 | 删，或改成具体做了什么。 |
| 面向未来，我们将继续探索更多可能性。 | 如果没有具体计划，删。 |
| 以用户为中心，构建完整生态体系。 | 改成具体服务谁、做什么；说不清就删。 |

## 常见 AI 味

| 问题 | 少用 | 更自然的方向 |
| --- | --- | --- |
| 作文结构 | 首先、其次、最后、综上所述 | 直接分段，必要时用小标题 |
| 报告腔 | 值得注意的是、我们可以看到、不难发现 | 直接说结论 |
| 自证式 | 我们不……是因为……；我们之所以……是因为…… | 去掉自我解释，直接写做法、结果或取舍 |
| 翻译腔 | 对于……而言、在……方面、具有……意义、被……所…… | 换成主谓宾，少搬英文被动和名词化 |
| 互联网黑话 | 赋能、抓手、闭环、链路、底座、心智、生态、沉淀、方法论、跃迁 | 换成具体动作、对象和结果 |
| 营销腔 | 助力、打造、新一代、全场景、一站式 | 换成具体功能或使用场景 |
| 空泛形容 | 高效、智能、极致、领先、完善 | 给指标、机制或场景 |
| 概念掰扯 | X 不是 X，而是 X；真正的 X 是 X；X 的本质是 X | 改成事实句，不下定义、不判高低 |
| 装饰过多 | ✅、🚀、✨、👉、📌、大量 icon 小标题 | 删掉符号，用分段、小标题或普通列表表达层次 |

## 六类高频问题

### 1. 翻译腔

翻译腔常见问题是主语虚、名词多、动词弱。英文翻译腔还会硬搬被动语态、名词化结构，或者把英文术语直译成中文里不常这么说的词。

| 原句 | 改法 |
| --- | --- |
| 对于开发者而言，该能力提供了更灵活的调用方式。 | 开发者可以按需选择调用方式。 |
| 该功能在提升协作效率方面具有重要意义。 | 这个功能让评审和修改可以在同一个页面完成。 |
| 这为后续扩展提供了良好基础。 | 后面新增 provider 时，只需要补一个适配器。 |
| 该请求会被系统自动处理。 | 系统会自动处理这个请求。 |
| 这个问题被广泛地讨论。 | 很多人都讨论过这个问题。 |
| 对错误进行处理。 | 处理错误。 |
| 完成对配置的更新。 | 更新配置。 |

常见误译词要按语境改，不要机械替换：

| 误译词 | 常见来源 | 更自然的方向 |
| --- | --- | --- |
| 光谱 | spectrum | 范围、分布、不同类型、不同程度 |
| 连续谱 | continuum | 连续范围、一系列状态、从 A 到 B 的变化 |
| 原语 | primitive | 基础能力、基础操作、基本元素、底层接口 |
| 令牌 | token | token / 凭证 / 词元，按技术语境选 |
| 提示 | prompt | prompt / 指令 / 提示词，按读者习惯选 |
| 管道 | pipeline | 流程 / pipeline，技术文档里可保留英文 |
| 工件 | artifact | 产物 / 文件 / 构建产物，按上下文选 |

### 2. 互联网黑话

互联网黑话常见问题是词很大，但不知道具体做了什么。遇到这类词，先问它指向哪个动作、对象或结果；说不清就删。

| 原句 | 改法 |
| --- | --- |
| 构建覆盖全链路的内容生产体系。 | 从选题、写稿到发布，都在后台完成。 |
| 打造面向企业增长的智能化底座。 | 企业可以把客户数据接进来，自动生成跟进建议。 |
| 形成产品、运营和数据协同的闭环。 | 产品看使用数据，运营按数据调整触达策略。 |
| 帮助团队沉淀可复用的方法论资产。 | 团队可以保存模板、例子和修改记录，下次直接复用。 |
| 以数据为抓手，持续赋能业务增长。 | 团队每周看一次转化数据，再调整投放和话术。 |

### 3. 概念掰扯

概念掰扯主要指用定义句、裁决句替代具体信息。常见写法是“X 不是 A，而是 B”“真正的 X 是 Y”“X 的本质是 Y”。如果后面没有具体事实，直接删掉这层判断。

| 原句 | 改法 |
| --- | --- |
| 它不是一个简单的写作工具，而是一套内容生产方法论。 | 它可以保存选题、模板和修改记录，适合团队反复写同类内容。 |
| 这不是一次功能升级，而是产品体验的系统性重构。 | 这次改了三个地方：导航更短、编辑器更稳、发布前能预览。 |
| 好的文档不是把功能讲全，而是让读者尽快完成任务。 | 好的文档要让读者尽快完成任务。功能细节放在需要的位置。 |
| AI 写作不是替代人，而是帮人更快整理想法。 | AI 写作可以先整理材料、列出草稿，人再判断和修改。 |
| 真正的增长不是流量增长，而是用户价值的持续兑现。 | 增长要看用户是否留下来、是否愿意继续付费。 |
| 这不是单点优化，而是一次端到端体验升级。 | 这次同时改了注册、配置、发布三个流程。 |

### 4. 平铺直叙不足

遇到绕很远才说重点的句子，把重点提前。

| 原句 | 改法 |
| --- | --- |
| 为了更好地满足用户在复杂场景下的多样化需求，我们对配置流程进行了优化。 | 配置流程改短了。复杂场景下，用户不用反复切页面。 |
| 随着业务规模不断扩大，原有方案逐渐暴露出一些问题。 | 业务量变大后，原方案有两个问题：慢，难排查。 |
| 在实际使用过程中，我们发现用户对结果可解释性有较高诉求。 | 用户想知道结果为什么这样生成。 |

### 5. 自证式口吻

自证式口吻常见于解释自己的动机，像“我们不……是因为……”“我们之所以……是因为……”。这类句子容易显得在自我辩护。多数情况下，删掉解释，直接写做法、结果或取舍。“体现、彰显、证明”这类词也常见，能删就删。

| 原句 | 改法 |
| --- | --- |
| 我们不追求功能堆砌，是因为我们更关注用户真正的核心需求。 | 我们只保留高频功能，低频配置放到高级设置里。 |
| 我们之所以选择这种设计，是因为它更符合开发者的使用习惯。 | 这种设计把配置项放在调用点旁边，开发者不用来回切文件。 |
| 我们不只是提供工具，而是希望陪伴用户完成整个创作过程。 | 用户可以在这里完成选题、写稿、修改和发布。 |
| 我们没有采用复杂方案，是因为简单才是最好的体验。 | 这个版本只保留两个步骤：上传文件，确认发布。 |
| 这充分体现了我们对开发者体验的重视。 | 我们把报错信息改成了可直接定位的问题。 |
| 该方案彰显了团队在工程实践上的深厚积累。 | 方案复用了现有 CI、日志和回放机制。 |
| 这证明了产品具备较强的市场竞争力。 | 过去 30 天有 42 家团队完成接入。 |

## 替代表达

不要机械替换，要看上下文。

| 原表达 | 可改为 |
| --- | --- |
| 通过 X，实现 Y | 用 X 做 Y / X 让 Y 可以…… |
| 基于 X，构建 Y | 用 X 做 Y / Y 依赖 X |
| 被 X 所 Y | X 会 Y / 由 X Y / 直接改主动句 |
| 对 X 进行 Y | Y X |
| 完成对 X 的 Y | Y X |
| 为用户提供了……能力 | 用户可以…… |
| 提升了使用体验 | 少一步操作 / 更快找到 / 错误更少 |
| 降低了使用门槛 | 不需要配置 / 不用写代码 / 新用户也能直接用 |
| 形成完整闭环 | 从 A 到 B 都在这里完成 |
| 赋能业务增长 | 帮业务多做了什么，直接写 |
| 以 X 为抓手 | 用 X 做什么，直接写 |
| 打造一站式平台 | 把哪些事放到一个地方做 |
| 有效解决……问题 | 解决了…… / 避免了…… |
| 具备良好的扩展性 | 新增 X 时只需要改 Y |
| 面向……场景 | 适合…… / 用在……时 |
| 进一步提升 | 让……更快 / 更少 / 更稳；说不清就删“进一步” |
| 持续沉淀 | 留下…… / 复用…… / 记录…… |
| 全链路 | 从 A 到 B / 包括 A、B、C |
| 底座 | 基础模块 / 公共服务 / 具体依赖 |
| 心智 | 用户记住什么 / 用户怎么理解 |
| 生态 | 哪些人、产品或服务一起用 |
| 不是 A，而是 B | 直接写 B；必要时补 A 和 B 的区别 |
| 真正的 X 是 Y | 改成“X 要看 Y”或直接写判断依据 |
| X 的本质是 Y | 改成具体机制；没有机制就删 |
| 我们不 X，是因为 Y | 直接写做法或取舍 |
| 我们之所以 X，是因为 Y | 直接写结果；必要时补一句依据 |

### 6. emoji 和 icon 过多

AI 生成内容常用 emoji、icon 和装饰性符号制造“活泼感”“重点感”或“层次感”。中文自然写作里，结构靠句子、分段和标题，不靠符号堆出来。除非是社交媒体、活动海报、聊天语境，或者用户明确要求保留，否则优先删掉。

| 原句 | 改法 |
| --- | --- |
| ✅ 支持多平台部署，🚀 快速上线，✨ 极致体验 | 支持多平台部署，可以更快上线。 |
| 👉 点击这里开始你的智能创作之旅 | 点击这里开始写作。 |
| 📌 核心亮点：高效、智能、稳定 | 核心亮点：更快生成初稿，支持保存修改记录，失败时可以重试。 |
| 🔥 全新升级，带来前所未有的使用体验 | 这次升级改了编辑器、预览和发布流程。 |
| 💡 小贴士：你可以通过配置参数来实现更灵活的控制 | 你可以调整参数来控制输出。 |

## 句式处理

### 长句拆短

原句：

> 通过引入结构化输出和可回放的测试机制，pyxis 能够在保证 LLM 灵活性的同时，为业务 agent 提供更稳定、可审计、可回归的执行边界。

可改：

> pyxis 用结构化输出和可回放测试约束 LLM 调用。业务 agent 仍然可以利用 LLM 的灵活性，但输出边界更稳定，也更容易审计和回归测试。

### 抽象变具体

原句：

> 该能力显著提升了开发者在复杂场景下的工程效率。

可改：

> 开发者不用再手写解析逻辑，也不用在每个调用点重复校验 LLM 输出。

### 自证改事实

原句：

> 这体现了我们对中文开发者真实需求的深刻理解。

可改：

> 这套写法优先服务中文开发者常见的 README、文档和 PR 场景。

### 互联网黑话改成人话

原句：

> 该平台通过构建智能化内容生产链路，帮助团队沉淀可复用的方法论资产。

可改：

> 团队可以在平台里写选题、生成初稿、保存修改记录。下次写同类内容时，可以直接复用之前的模板和例子。

### 概念掰扯改平实陈述

原句：

> 好的 prompt 不是把要求写得越多越好，而是让模型知道当前任务最重要的约束。

可改：

> 好的 prompt 要写清楚当前任务最重要的约束。要求太多时，模型反而容易抓不住重点。

### 翻译腔改主谓宾

原句：

> 对于需要频繁处理客户反馈的团队而言，该功能在提升响应效率方面具有重要价值。

可改：

> 需要频繁处理客户反馈的团队，可以用这个功能自动归类问题，更快分给对应负责人。

## 场景样例

### README

改前：

> 本项目旨在打造一个高效、可靠、可扩展的智能 Agent 开发框架，帮助开发者快速构建面向复杂业务场景的 AI 应用。

改后：

> pyxis 把一次 LLM 调用写成 Python 函数，返回 Pydantic 实例。它适合需要结构化输出、回归测试和机器消费结果的 agent 场景。

### 产品文案

改前：

> 新一代智能协同平台，全面赋能企业内容生产全链路，助力团队实现效率跃迁。

改后：

> 团队可以在一个地方完成选题、写稿、评审和发布。每一步都有记录，后面追改更方便。

### UI 文案

改前：

> 当前操作无法完成，请检查相关配置是否正确后重试。

改后：

> 保存失败。请检查配置后再试。

如果能知道具体错误，就写具体错误：

> 保存失败。API key 为空。

### PR 描述

改前：

> 本 PR 主要对 Step 模块进行了优化，进一步提升了代码可维护性和整体稳定性。

改后：

> 这个 PR 调整了 Step 的参数透传逻辑。`params` 现在会原样传给 provider API，pyxis 不再枚举或校验字段。

### PPT 标题

改前：

> 方案价值

改后：

> 结构化输出让 LLM 结果可以测试、审计和回放

### 社交媒体

改前：

> 在当今快速变化的时代，如何更好地提升个人表达能力，已经成为每个人都需要面对的重要课题。

改后：

> 很多人不是没想法，是一写出来就太绕。

## 审校输出格式

用户要求“帮我看哪里 AI 味”时，用这种格式：

```markdown
主要问题：
- 句子太满，但具体信息少。
- 有几处报告腔和自证式表达。

建议改法：
[改写稿]

改动点：
- 删除了“充分体现”“持续赋能”这类自证式说法。
- 把“提升体验”改成了具体行为。
```

用户只要求“改自然一点”时，不解释，直接给改写稿。
